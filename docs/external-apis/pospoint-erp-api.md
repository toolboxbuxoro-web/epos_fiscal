# Pospoint ERP API — выжимка для интеграции

Источник: «Pospoint ERP API — руководство интегратора», приложение 1.0.591,
протокол 1.0.2 — https://doc.clickup.com/9018751508/d/h/8cryegm-3798/f9411415dbce99c
(11 страниц + Postman-коллекция). Прочитано 09.11.2026. Pospoint — кассовая
программа «мобильная касса» (кабинет mobkassa.uz), заменяет у нас E-POS
Communicator. Здесь — только то, что важно для нашей кассы, своими словами.

## Как устроено

Программа Pospoint стоит на компьютере кассы и слушает `http://127.0.0.1:6461`.
Наша касса шлёт `POST /pospoint`, Pospoint подписывает чек в ФМ и сам отправляет
в ОФД (сразу и раз в час, пока открыт). `GET /health` → `{"status":"UP"}` —
жив ли сервер (ФМ не проверяет, отвечает даже когда касса занята).

Сервер работает, только пока приложение открыто, выполнен вход и включены
«Кассовый режим» и «Режим интеграции». **После входа по логину и паролю режим
интеграции выключается** — его надо включить снова (значок в верхней панели).

## Запрос и ответ

```json
{ "method": "registerSaleFull", "id": "435645", "key": "<ключ кассы>", "version": "1.0.2", "params": {} }
```

- Все пять полей обязательны. `version` — ровно `"1.0.2"` (выше → 14801).
  `id` — только цифры (иначе 14822). `params` для методов без параметров — `{}`.
- Ответ: `{"id":…, "result":{…}}` или `{"id":…, "error":[{code, message, data?}]}`.
  `error` — **всегда массив**. HTTP-статус всегда 200. Поля со значением null
  не приходят.
- Касса выполняет запросы **строго по одному**. Таймаут на нашей стороне — не
  меньше 60 с (у нас 90 с на чек).
- Ключ кассы выдаёт Pospoint. Публичный тестовый ключ
  `41192fcccd93a9097843057e60e1da1904798f9f` проверяет формат registerSaleFull
  и отвечает случайными данными — ФМ, ОФД, каталог не трогает, payCheckNumber
  не проверяет.

## Единицы

| Что | Формат |
|---|---|
| Суммы и цены | **сумы**, до 2 знаков (лишние отбрасываются без округления) |
| `price` | цена **за единицу** |
| `discount` позиции | сумма скидки на всю позицию, сумы |
| Количество | число, для весового — дробное |
| Время | unix ms |
| `taxPercent` | 0, 6 или 12; НДС включён в цену, касса считает его сама |
| X-отчёт (`getXReport`) | суммы в **тийинах** |
| Z-отчёт (`closeZReport`) | суммы в **сумах** — не перепутать |

Сумма чека: Σ(price × amount − discount) − discount чека = byCash + byCard,
допуск ±50 сум (иначе 14807).

У нас цена за единицу — всегда целые сумы (вверх), излишек — в `discount`
позиции: сумма чека совпадает до тийина, а у возврата цена та же, что в
продаже (см. `toPospointItem`).

## Методы, которые используем

| Метод | Зачем |
|---|---|
| `registerSaleFull` | продажа с данными о товаре (наименование, `unit`, `packageCode`, `mxik`, `ownerType`, `amount`, `price`, `taxPercent`, `discount`, `barcode`); чек: `items`, `byCash`, `byCard`, `type: "SALE"` (обязательно, заглавными), `payCheckNumber`, `cardType` (1 — корпоративная, 2 — личная), `print` |
| `registerRefundFull` | возврат: `idRefundReceipt` (= `result.id` продажи на ЭТОЙ кассе), позиции (`name`, `mxik`, `amount`, `price` за единицу из продажи), `byCash`/`byCard`, свой `payCheckNumber` |
| `getReceiptByPayCheckNumber` | найти чек по нашему номеру документа; не найден — пустой `result` |
| `openZReport` / `getXReport` / `closeZReport` | смена; открывается сама на первом чеке; `getXReport` при закрытой смене → -14 |
| `checkFmStatus` | ФМ подключён? `unsentReceiptCount`. На апплете 4 первый вызов может привязать ФМ к кассе (POS Lock) |
| `syncWithOfd` | отправить в ОФД сейчас (на Windows до 32 чеков за вызов, повторять пока `unsentCount > 0`) |
| `syncFmState` | при ошибке 37008 (ФМ требует синхронизации) |
| `getMxikInfo` | справочник tasnif: по ИКПУ → `packages[{code, nameRu}]` — откуда берём `unit` |

`unit` и `packageCode` касса не проверяет, но без них позиция уходит с кодом 0
и без названия единицы — передаём всегда.

## Ответ на чек

`id` (номер чека, нужен для возврата), `fmNo`, `kkmNo`, `time` (unix ms),
`url` (ссылка для QR), `fiscalSign`. `shiftNumber` через API сейчас не приходит.

## Надёжная отправка

1. `payCheckNumber` — уникальный номер нашего документа (у возврата свой).
2. Пришёл `result` с `id` и `fiscalSign` — готово. Пришёл 14824 — чек уже
   пробит раньше: забрать `getReceiptByPayCheckNumber`.
3. Ответа нет, -13, -32603, -32099 или код ФМ — результат неизвестен: сначала
   `getReceiptByPayCheckNumber`; нашёлся — готово. Не нашёлся — **до повтора
   сверить `getXReport`** (документация): ФМ мог подписать чек, а Pospoint —
   не записать номер. Счётчики не сдвинулись — можно повторять.
4. **После входа по логину/паролю или смены организации касса удаляет из своей
   базы уже отправленные чеки** — поиск, возврат и защита 14824 по ним
   перестают работать.

Как это сделано у нас (`pospoint.ts`, `sendWithRecovery` и журнал попыток):

- «Неизвестно» — это ещё и обрыв соединения после отправки, пустой/не-JSON
  ответ, пустой массив `error`, `result` без `id` или `fiscalSign`. Точно не
  ушёл чек, только если соединение не установилось (refused, нет хоста).
- Поиск ждёт до 60 с и делает 3 попытки: он встаёт в очередь кассы за
  зависшим чеком.
- X-отчёт снимаем до отправки; после неудачного поиска сдвинулись счётчики
  (или сравнить не по чему) — документ блокируется до сверки человеком.
- «ФМ не найден» (4240, 4100) — чек точно не пробит: подписать было нечем,
  документ не блокируется. X-отчёт после сбоя читаем до трёх раз.
- Попытка пишется в журнал до отправки и снимается после записи в нашу БД:
  повтор документа сначала разбирает прошлую попытку, а не шлёт новый чек.

## Возврат

- Только на той кассе, где пробита продажа (иначе 36872). Чек registerSaleFull —
  только через registerRefundFull.
- Количество не больше проданного (14811). Касса не суммирует возвраты — считаем
  сами.
- byCash + byCard — не больше стоимости позиций с учётом скидок и суммы продажи
  (14807).
- Лимиты ФМ: возврат не больше продаж текущей смены этим способом оплаты —
  36913/36914 (апплет 3), 36917 (апплет 4).
- Позицию продажи касса ищет по `mxik` или `barcode`, по `name` — только если
  нет ни того, ни другого. В одном чеке ИКПУ повторяется часто (у нас 15 %
  чеков), поэтому шлём только однозначный ключ: ИКПУ, если он в продаже один;
  иначе штрихкод, если он один; иначе только название.
- Перед возвратом сверяем `getReceipt(idRefundReceipt)`: признак должен
  совпасть с нашим (после повторного входа номера в Pospoint начинаются
  заново).

## Ошибки (главное)

| Код | Смысл | Что делаем |
|---|---|---|
| 14800 | неверный ключ | «проверьте ключ кассы» |
| 148xx, -32602 | неверный запрос | наша ошибка — техническая, в лог |
| 14824 | уже пробит | берём поиском |
| -10 / -12 | касса не активна / фискальный режим выключен | сообщение кассиру |
| -14 | смена не открыта (getXReport) | экран «Смена не открыта» |
| -15 | продажа только по карте (УП-246) | сообщение кассиру |
| -13, -32603, -32099, коды ФМ | результат неизвестен | поиск по номеру |
| 4240 / 4100 | ФМ не найден | «проверьте USB-ридер» |
| 36886, 36889 (апплет 3), 36913, 37105 (апплет 4) | память ФМ / неотправленные чеки | `syncWithOfd`, повтор |
| 37008 | ФМ требует синхронизации | `syncFmState`, повтор |
| 37011 | POS_AUTH_FAIL | поддержка Pospoint |
| 36888, 36912 (апплет 4), 36916 | время чека в прошлом | «проверьте дату и время» |
| 36911, 36928–36933 | переполнение смены | «закройте смену» |

Внимание: одни и те же коды ФМ значат разное на апплетах 3 и 4 (36912 — «смена
уже открыта» на 3 и «время в прошлом» на 4; 36913 — «нет наличных для возврата»
на 3 и «неотправленные чеки» на 4; 36897 — «время закрытия в прошлом» на 3 и
«смена не открыта» на 4). Версию апплета узнаёт фоновая проверка
(`checkFmStatus` → `appletVersion`); пока не знаем — трактуем по операции.
`checkFmStatus` на апплете 4 может привязать ФМ к кассе (POS Lock), поэтому до
переключения кассы на Pospoint мы его не вызываем.
